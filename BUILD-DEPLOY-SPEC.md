# Ultra-Water — production-білд, Netlify та перенесення проєкту

Статус: реалізовано локальний білд та підготовку CLI-деплою, 2026-11-18.
Результати перевірки наведені в §9; публікація на Netlify виконується окремою командою.

Область: конфігурація білду й адаптер Tilecraft у цьому репозиторії.
Checkout Tilecraft лише читається; його вихідні файли не змінюються.
Цей документ замінює обмеження «збірка з полем — не мета v0.1» у
[spec.md](spec.md) §3.2 для нової реалізації production-інтеграції.
Рендеринг, фізика та поведінка фреймів залишаються предметом своїх специфікацій.

## 1. Очікуваний результат

`npm run build` створює самодостатню папку `dist/`: океан, Tilecraft-компілятор,
обидва конвеєри тайлів, моделі й sidecar-файли. Її можна завантажити на Netlify
без Node.js-сервера, доступу до локального диска або сховища R2.

Папку Ultra-Water можна перемістити між такими розташуваннями:

| Розташування Ultra-Water | Якщо Tilecraft лишається на місці |
|---|---|
| `D:/work/_tools/water-3d/Ultra-Water` | без змін конфігурації |
| `D:/work/_tools/Ultra-Water` | без змін конфігурації |
| `D:/work/Ultra-Water` | без змін конфігурації |

Якщо переміщується сам Tilecraft, користувач змінює **одне значення**
`TILECRAFT_ROOT`, перезапускає dev-сервер або повторює білд. Зміни JS-коду,
alias, списку ресурсів і Netlify-конфігурації для цього не потрібні.

## 2. Причина поточної несправності

- `vite.config.js` дозволяє Tilecraft лише при `command === 'serve'`, а під час
  білду підставляє порожній `__TILECRAFT_ROOT__`.
- `src/tiles/tilecraftLoader.js` імпортує модулі через `/@fs/` та
  `/* @vite-ignore */`. Ці модулі не потрапляють у production-бандл.
- `/@fs/` обслуговує локальний Vite, а звичайний статичний хост такого API не має.
- Tilecraft `core/model-loader.js` визначає адреси моделей від свого
  `import.meta.url`. Після бандлінгу місце JS змінюється; JSON та sidecar зараз
  взагалі не включені в `dist/`.

Самої заміни `ROOT` на HTTP-адресу недостатньо: зовнішні JS-модулі також
імпортують `three` та інші залежності, які має обробити збирач.

## 3. Одне налаштування розташування Tilecraft

### 3.1 Локальна конфігурація

У корені Ultra-Water створити незакомічений `.env.local`:

```dotenv
TILECRAFT_ROOT=D:/work/js-games/ua-dream/tilecraft
```

Використовувати прямі слеші. Значення може містити пробіли; конфігурація має
коректно обробляти такий шлях. Не використовувати префікс `VITE_`: це шлях
для Node.js-конфігурації, його не потрібно передавати браузеру.

Додати `.env.local` і `.env.*.local` до `.gitignore`, а `.env.example` — у Git.
У прикладі достатньо одного рядка з поясненням, що потрібно вказати абсолютний
шлях до свого checkout. Сам `.env.local` переміщується разом із папкою проєкту,
хоча Git його не переносить при новому клонуванні.

При новому клонуванні користувач один раз створює `.env.local`. При фізичному
переміщенні всієї папки з цим файлом повторна конфігурація не потрібна.

### 3.2 Правила визначення шляху

Винести визначення коренів у Node.js-модуль, наприклад
`build/tilecraft-config.js`, який використовується Vite та скриптами перевірки.

1. `projectRoot` визначати від URL самого конфігураційного модуля, а не від
   `process.cwd()` і не від поточного абсолютного розташування Ultra-Water.
2. Завантажувати Vite env для поточного mode з `projectRoot` через `loadEnv`.
3. Явна змінна `process.env.TILECRAFT_ROOT` має пріоритет над значенням з env-файлів.
   Це дозволяє CI використовувати власний шлях без редагування файлів.
4. За відсутності непорожнього значення завершувати запуск із підказкою створити
   `.env.local`. Не мати прихованого запасного `D:/...` у JS.
5. Абсолютний шлях використовувати без прив'язки до Ultra-Water. Якщо користувач
   свідомо задає відносний шлях, розв'язувати його від `projectRoot` і пояснити
   в README, що після перенесення він може потребувати зміни.
6. Перевіряти існування потрібних модулів і ресурсів, нормалізувати шлях для
   Vite та коректно працювати з Windows drive letters, пробілами й symlink.

Абсолютні шляхи до Tilecraft та Ultra-Water дозволені в локальних діагностичних
повідомленнях, але не в опублікованих JS, HTML чи метаданих білду.

Усі власні файлові операції конфігурації, зокрема читання
`THIRD_PARTY_NOTICES.md`, виконувати від `projectRoot`. Задати Vite `root`
явно, щоб власна конфігурація не залежала від випадкового робочого каталогу.

## 4. Імпорт коду Tilecraft

Використовувати один механізм інтеграції в dev і build:

- alias `@tilecraft` → перевірений `TILECRAFT_ROOT`;
- `resolve.dedupe: ['three']` зберегти;
- dev `server.fs.allow` дозволяє потрібний зовнішній checkout;
- порт локального стенда залишається `5199`, `strictPort: true`.

У `tilecraftLoader.js` прибрати ручне складання `/@fs/` URL,
`/* @vite-ignore */`, `THREE_DIR` та браузерний абсолютний `ROOT`.
Використовувати явні літеральні імпорти, видимі Vite, наприклад:

```js
await import('@tilecraft/lib/thickness-scale.js');
await import('@tilecraft/viewer/engines/pixi/polyline-lcr.js');
const loader = await import(
  '@tilecraft/viewer/engines/three/core/model-loader.js'
);
```

Так само явно імпортувати `coordinates`, `world-config`, `scene-compiler`
і `resource-scope`. Не замінювати це динамічно складеним шляхом `at(path)`.

Зберегти lazy loading та кешування promise. Порядок двох IIFE-скриптів
обов'язковий: спочатку `thickness-scale`, потім `polyline-lcr`, після цього
компілятор. У разі відмови завантаження кеш скидається, повторна спроба можлива.

Відсутність Tilecraft — помилка запуску/білду, а не успішний production-білд
із мовчки вимкненими плитками. `tilecraftAvailable`, якщо потрібен наявному UI,
більше не залежить від абсолютного шляху в браузері.

Не копіювати дерево вихідного коду Tilecraft у `src/` або Git Ultra-Water.
У `dist/assets/` потрапляє лише зібраний код із реально потрібними залежностями.
Єдиний екземпляр `three` обов'язковий: `sameThree === true` при компіляції.

## 5. Ресурси моделей та URL

### 5.1 Явний список публікації

Створити один manifest ресурсів у build-модулі Ultra-Water. Для нинішнього
`TILE_SOURCES` необхідні такі файли відносно кореня Tilecraft:

| Файл | Для чого |
|---|---|
| `.pw-probe/story-rombs-gd.json` | спільні вихідні байти трьох story-варіантів |
| `.pw-probe/story-rombs-gd.frames.json` | sidecar орієнтацій фреймів |
| `viewer/engines/three/fixtures/world-demo.json` | модель `demo` |
| `viewer/engines/three/fixtures/world-demo.world.json` | world-конфіг `demo` |

Копіювати тільки цей явний список, не весь `.pw-probe/`, `viewer/` чи checkout.
Інші fixtures не входять у підтримуваний перелік застосунку; додавання нового
джерела передбачає оновлення manifest і перевірки повноти ресурсів.

JSON копіювати байт у байт: не міняти форматування, кодування або закінчення
рядків. Fingerprint моделі та зв'язок із sidecar мають зберегтися.
Якщо потрібного файла немає, білд завершується помилкою навіть тоді, коли
runtime-loader вважає sidecar необов'язковим.

### 5.2 Структура виходу

Vite-плагін емітить ресурси з такими іменами:

```text
dist/
  index.html
  assets/                         # зібрані JS-чанки, включно з Tilecraft
  tilecraft/
    models/
      story-rombs-gd.json
      story-rombs-gd.frames.json
    viewer/engines/three/fixtures/
      world-demo.json
      world-demo.world.json
  licenses.md
  THIRD_PARTY_NOTICES.md
```

Вихідні story-файли читаються з `.pw-probe/`, але публікуються під `models/`.
Netlify CLI 27.20.0 виключає dot-каталоги під час підготовки upload, тому
збереження `.pw-probe/` у публічному шляху не допускається. Manifest є єдиним
місцем зіставлення вихідного файла й вихідного URL. Інші probe-файли не копіюються.

### 5.3 Адаптація `model-loader.js` без зміни Tilecraft

Не дублювати `loadFixture`, `FIXTURE_MODIFIERS`, парсинг або fingerprint у
Ultra-Water. Перетворення `hibrid` та `polygon` виконує оригінальний loader.

У build-плагіні адаптувати визначення `STAND_ROOT` і побудову URL ресурсу в конкретному
`viewer/engines/three/core/model-loader.js` із вибраного checkout. Замість
кореня від URL JS-модуля використовувати URL
`<Vite base>/tilecraft/viewer/engines/three/` на origin застосунку.
Це адреса каталогу з обов'язковим завершальним `/`.

За `base: '/'` loader має отримати такі адреси:

```text
./fixtures/world-demo.json
  → /tilecraft/viewer/engines/three/fixtures/world-demo.json
../../../.pw-probe/story-rombs-gd.json
  → /tilecraft/models/story-rombs-gd.json
```

Реалізація може використати virtual module із публічним base URL. Не залишати
`import.meta.url` зібраного JS як основу шляхів моделей. Підтримати звичайний
pathname `base` Vite, зокрема `/` і `/water/`; відносний `base: './'` у цій
реалізації не потрібен, його слід явно відхиляти або окремо реалізувати.

Перетворення має бути вузьким і перевіреним: очікуване визначення `STAND_ROOT`
повинно зустрітися рівно один раз. Якщо контракт Tilecraft змінився, завершити
білд із зрозумілою помилкою, а не випускати сайт із неправильними URL.
Так само перевіряти рівно один виклик `new URL(path, STAND_ROOT).href` і
замінювати його версією, яка переводить `../../../.pw-probe/` у `../../../models/`.
Це лише адаптація адрес: модифікатори, завантаження й fingerprint не дублюються.
При зміні коду забезпечити коректну sourcemap для dev-діагностики.

У dev той самий плагін віддає manifest ресурсів за тими самими публічними URL,
читаючи їх наживо з Tilecraft. Обробник приймає тільки точні manifest-шляхи;
довільне читання файлів за URL та path traversal не допускаються.
Старий загальний regex-плагін `tilecraftAssetUrls()` замінити цим вузьким
адаптером; інші залежності з asset URL перевірити під час інтеграції.

## 6. Команди та публікація

Після реалізації звичайний локальний сценарій у корені Ultra-Water:

```powershell
npm ci
npm run dev
```

Для релізу:

```powershell
npm run build
npm run preview -- --host 127.0.0.1
```

Перевірити preview, потім завантажити **всю папку `dist/`** на Netlify.
Старі JS-чанки не змішувати з новими моделями: публікувати один цілісний білд.
На хості не потрібні `TILECRAFT_ROOT`, вихідні checkout або R2-клієнт.
Запускати сайт через HTTP(S), не через `file://`.

Зафіксувати Node.js `24` у `.node-version` та описати його в README.
`package-lock.json` залишається в Git; установка для перевірки — `npm ci`.
Ліцензії залежностей і потрібні повідомлення Tilecraft включити в артефакт;
перевірити фактичні умови його коду та моделей перед публікацією.

Для майбутнього білду безпосередньо на Netlify:

```toml
[build]
  command = "npm run build"
  publish = "dist"

[build.environment]
  NODE_VERSION = "24"
```

Цей конфіг сам по собі не доставляє Tilecraft у CI. Перед білдом CI має
отримати checkout за зафіксованою ревізією та передати `TILECRAFT_ROOT` до
його абсолютного Linux-шляху. Не передавати Windows-шлях із локального ПК.
Автоматизація отримання приватного checkout — окреме завдання; перший
результат цієї специфікації — локальний білд і ручна публікація `dist/`.

R2 не входить у цю реалізацію. Якщо пізніше моделі оновлюватимуться незалежно
від коду, додати окремий контракт URL/версій ресурсів; не переносити браузерні
імпорти компілятора на `/@fs/` або S3 API.

## 7. Перевірки приймання

### 7.1 Перенесення та конфігурація

1. На початковому шляху створити `.env.local` з абсолютним `TILECRAFT_ROOT`;
   виконати білд і перевірку production-сайту.
2. Перевірити той самий проєкт у кожному з двох інших розташувань із §1.
   Tilecraft та `.env.local` не змінювати; `npm run build` має проходити.
   Для перевірки можна використати тимчасову копію: оригінальну робочу папку
   не переміщувати без окремої потреби. Для іншої ОС/середовища виконати `npm ci`.
3. Для іншого checkout Tilecraft змінити тільки `TILECRAFT_ROOT` або задати
   його через process env. Перевірити пріоритет env над `.env.local`.
4. Відсутній, порожній і неправильний шлях дають явну помилку до успішного
   завершення білду. Окремо перевірити шлях із пробілами.
5. Власні скрипти перевірки не містять абсолютного шляху до Ultra-Water.

### 7.2 Самодостатність білду

- На час production-перевірки зробити вихідний Tilecraft недоступним процесу
  статичного сервера: сервер читає лише `dist/`. Не перейменовувати й не
  видаляти користувацький checkout для цієї перевірки.
- Відкрити `/`, потім усі чотири `TILE_SOURCES` через UI і `?tiles=<id>`.
  Успішно завантажуються моделі, world-конфіг і sidecar; у Network немає 404
  на потрібні ресурси й немає запитів `/@fs/`, `localhost` або Windows-шляхів.
- Завантажити локальний JSON через file input і drag & drop. Для цього
  використовуються той самий запакований компілятор і наявний `loadFile`.
- Перевірити `sameThree === true`, polygon та polyline/LCR у гібридній моделі,
  перемикання фреймів, anchored/drift і перенесення фреймів на сушу та воду.
- Перевірити SHA-256 кожного опублікованого JSON проти вихідного файла.
- Повторити URL-перевірку з `base: '/water/'` на статичному сервері під цим
  префіксом. Збережені URL-параметри моделей мають працювати після reload.
- Перевірити вихідні HTML/JS: немає `D:/work`, локальних коренів checkout,
  `/@fs/`, нерозв'язаних `@tilecraft` або `__TILECRAFT_ROOT__`. Публічні
  production-sourcemap у першій реалізації вимкнені.
- Після ручної публікації повторити чотири джерела, локальний файл і reload
  на `https://edge-of-elements.netlify.app/`, включно з `tilecraft/models/`.

### 7.3 Межі перевірки

Успішний `vite build` сам по собі не є прийманням: потрібен запуск зібраної
версії у браузері з WebGL2. Наявні перевірки tile/frame поведінки запускати
відповідно до змінених модулів; перенесення URL не повинно міняти фізику.
Dev-стенд на `http://localhost:5199/` лишається запущеним за правилом AGENTS.md;
production перевіряти окремим сервером/портом, не підміняти ним dev-стенд.

## 8. Порядок реалізації та документація

1. Єдиний resolver шляхів, `.env.example`, ignore-правила та preflight перевірки.
2. Alias та явні імпорти Tilecraft; один екземпляр `three`.
3. Manifest, dev-віддача ресурсів, emit у `dist/` та адаптація `STAND_ROOT`.
4. Локальний production smoke test, перевірка перенесення та Netlify deploy.
5. Оновлення README: налаштування одного шляху, dev/build/preview, ручний deploy,
   вимоги до CI; узгодження старої примітки у `spec.md` з реалізованим станом.

Не створювати додаткових місць, де користувач має редагувати шлях Tilecraft.
Не вважати роботу завершеною, якщо `dist/` відображає лише океан, а джерела
Tilecraft вимкнені або залежать від запущеного Vite dev-сервера.

## 9. Команди реалізованої збірки й деплою

- `npm run build` / `make build`: збірка й перевірка байтів ресурсів, notices,
  відсутності локальних runtime-шляхів, dot-файлів і публічних sourcemap.
- `npm run test:build` / `make test`: Chromium, усі джерела, спільний three,
  sidecar, world-конфіг, frame/mode, локальний файл і drop, `/water/` base.
- `npm run test:portability` / `make test-portability`: збірка копій на різній
  глибині та в папках із пробілами; checkout може бути junction/symlink.
- `npm run deploy:check` / `make deploy-check`: свіжий білд і підготовка
  CLI-команди без відправлення даних.
- `npm run deploy` / `make deploy`: свіжий білд, перевірка, draft deploy.
- `npm run deploy:prod` / `make deploy-prod`: свіжий білд, перевірка, production.

Скрипт `scripts/deploy-netlify.mjs` запускає локальний зафіксований Netlify CLI
з `--no-build --dir dist`. Ціль: явний `--site`, `NETLIFY_SITE_ID`, linked
`.netlify/state.json`, інакше існуючий `edge-of-elements`. Автоматичного
створення нового проєкту немає. Токен за потреби передається лише через
`NETLIFY_AUTH_TOKEN`, не в аргументах чи логах. CLI-залежності зафіксовані
в `package-lock.json`; GNU Make — необов'язкова зовнішня утиліта.
