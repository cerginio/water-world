# Перенесення фреймів по воді й рельєфу

Статус: проєкт спеки v0.2, 2026-11-02. Реалізації ще немає.
Розширює [spec.md](spec.md): знімає заборону контакту поля з берегом.
Не змінює Tilecraft і не вимагає промоції в CPU Body.
Попередні розділи про незалежний дрейф діють для вільних фреймів.

Термінологія: **фрейм** — фрейм моделі Tilecraft (`frameId`); **кадр** — лише
кадр рендеру («мс/кадр», «щокадровий»).

Зміни v0.2 проти v0.1: точний контакт по трикутниках видимого меша замість
растрової карти; pose фрейму в рендері — матриця об’єкта, у симуляції —
uniform-масив; без GPU snapshot; без yaw у v0.1; синхронний picking на down;
контакт із землею для всіх тайлів; polyline укладається по тайлах, без
subdivision; правило перекриття фреймів; виправлено праву кнопку миші;
без користувацького скасування drag (лише системне); pose placed-фрейму
тримається у світі при повороті/переміщенні поля.

## 1. Очікувана поведінка

Користувач хапає малюнок за видиму деталь і пересуває **весь фрейм**, а не
окремий тайл, групу або всю модель. Працюють миша, перо та один палець.
Точка захоплення залишається під вказівником. Повторний захват можливий
на воді, березі та суші.

Фрейм поводиться як гнучкий набір плиток і стрічок:

- XZ-розташування деталей зберігається під час перенесення; вертикаль
  пристосовується до води й землі. Немає масштабування малюнка від жесту.
- На воді він продовжує слідувати хвилям. Суша дає нерухому опору, схили
  нахиляють плитки, polyline повторює профіль рельєфу.
- Перехід відбувається по ділянках: берег не перемикає весь фрейм одним прапорцем.
- Після відпускання фрейм залишається на новому місці. Хвилі впливають на
  плаваючу частину, але не зсувають закріплений малюнок цілком.

Під «згідно рельєфу» тут розуміється видима поверхня острова: пісок, пагорби,
схили та підводне дно. Декоративні камені, дерева, стовбури, скелі з нависаннями
не є опорою v0.2. Фрейм може перетинати такі пропи; це явно відмінний від
контакту із землею обсяг робіт.

Контакт із землею (§7–§8) діє на **всі** тайли, не лише на перенесені:
inherited-фрейм, який дрейф виніс на мілину, теж зупиняється на дні або
березі, а не проходить крізь острів.

## 2. Керування

| Дія | Миша / перо | Touch |
|---|---|---|
| Вибрати фрейм | Короткий клік по його видимій деталі | Короткий tap |
| Перенести | Ліва кнопка / кінчик пера, рух понад 5 CSS px | Один палець, рух понад 10 CSS px |
| Камера | Звичайні жести на порожньому місці; над фреймом права кнопка — pan, середня — zoom (типові кнопки OrbitControls) | Один палець на порожньому місці; два пальці для камери |
| Завершити | Відпустити кнопку | Підняти палець |

Окремої дії «скасувати перенесення» немає: щоб повернути фрейм, його
перетягують назад; режим повертає «Відпустити у дрейф» (§5). Скасування
лишається тільки системним — для збоїв вводу (нижче).

Обертання камери над фреймом лівою кнопкою неможливе — вона тягне фрейм;
обертання починається з порожнього місця. Розкладку `mouseButtons` не змінюємо.

Захват починається тільки на canvas. GUI, HUD та кнопки не починають перенос.
Hover дає стримане підсвічування доступного фрейму; на touch вибір видно після tap.
Під час drag підсвічується весь фрейм, а не тільки натиснута група. Заливка
малюнка та його прозорість не змінюються; перевага окремому контуру/маркерам.

### Арбітраж вводу

Обробник `pointerdown` у capture-фазі на canvas виконує **синхронний** picking
(§3) до того, як подію побачить `OrbitControls`:

- hit → `stopImmediatePropagation`, OrbitControls цей pointer не отримує;
  клік без подолання порога лише вибирає фрейм;
- miss → подія йде далі без змін, камера стартує без затримки.

Так немає ані затримки старту камери, ані повторного відтворення pointerdown.
Ціна — одна зупинка GPU на down; її вимірюють (§11).

Другий touch завершує перенос у поточному місці й передає камері обидві точки:
для першого пальця, якого OrbitControls не бачив, відтворюється синтетичний
`pointerdown` у його поточній позиції, другий проходить штатно. Це єдиний
випадок відтворення подій. Відпускання pointer поза canvas завдяки pointer
capture теж завершує drag. `pointercancel`, втрата capture, blur або зміна
джерела скасовують drag (системне скасування). Контроли камери відновлюються
в усіх виходах.

У v0.2 одночасно переноситься один фрейм. Обертання фрейму (yaw), підйом у
повітря, кидок, мультивибір і редагування окремих деталей — поза обсягом.

## 3. Що саме захоплюємо

Одиниця ідентичності — `frameId` із моделі, а не індекс у GUI. Один фрейм може
містити polygon і polyline кількох шарів; усі вони переміщуються разом.
Потрібні щільний `frameIndex` і таблиця відповідності вихідним id.
Числовий `2` та рядковий `"2"` не можна довільно зливати; нормалізація URL
виконується за відомими id конкретної моделі.
Тайли без frameId утворюють окремий синтетичний фрейм цього source;
вони не потрапляють випадково до фрейму з id=0.

Кожен render-меш уже належить рівно одному фрейму (`collectTileRest` будує
частини за `record.frameId`). Цей інваріант обов’язковий: на ньому тримається
pose у рендері (§6).

Верхня видима деталь визначає вибраний фрейм. Порожнє місце всередині його
прямокутника не є hit. Для маленьких touch-цілей дозволено picking у радіусі
6 CSS px: спочатку центральний pixel, потім найближчий до центру hit. ID pass
має depth test, тож у кожному pixel вже записаний верхній фрейм; окремого
правила «ближчий до камери» немає.

CPU Raycaster по rest-мешах непридатний: реальна геометрія змінюється на GPU.
Основний варіант — GPU ID picking тими самими мешами й тим самим vertex
deformation, що й видимий матеріал (state, frame pose через matrixWorld,
`aSurfaceOffset`). Вихід — frameIndex+1, фон=0; color management, blending і
MSAA вимкнені. Прозорі ділянки з alpha <0.1 не дають hit. Обробка відсікання й
видимості узгоджена з основним проходом. Острів та непрозорі пропи записують
depth, але не frame id, щоб не хапати фрейм крізь пагорб.

Picking лише за запитом, не щокадровий повнорозмірний readback:

- **down** — синхронний `readPixels` ділянки 13×13 device px навколо pointer;
  рендер ID pass обмежений scissor цієї ділянки (з урахуванням CSS розміру,
  DPR та неповного viewport);
- **hover** (лише миша/перо) — асинхронний, не частіше одного запиту за кадр,
  через `readRenderTargetPixelsAsync`, як у `WaterQuery`. Результат містить
  pointer generation і source epoch; застарілий відкидається.

Синхронний readback під час move заборонений.

## 4. Точка руху під мишею

Перетягування — зміна world XZ, висоту задають опорні поверхні.
Звичайний перетин з площиною y=0 на схилі дає помилку паралаксу, тому його
недостатньо для фінальної цілі drag.

Потрібен `SurfaceCursor`: промінь камери перетинається з верхньою доступною
поверхнею води/землі. Земля — та сама контактна поверхня, що використовує
малюнок (§7); вода — узгоджена з `waterAt`. На down зберігається XZ-різниця між
точкою захоплення і pivot фрейму; вона не обнуляється при перетині берега.

Для води: перетин із горизонтальною площиною на останній відомій висоті точки
захоплення; уточнення — через наявний асинхронний `WaterQuery`, без
синхронного readback у move. Для землі: точний перетин промінь–трикутники
heightfield (§7) крокуванням по комірках сітки. Перевіряється реальна висота
точки захоплення з осадкою/товщиною, щоб плитка залишалася під вказівником, а
не її проєкція на дно. Один-два коригувальні кроки за останньою опорною
висотою допустимі; вони не змінюють grab offset.

Якщо промінь спрямований у небо, майже паралельний поверхні або виходить за
дозволену область, позиція лишається останньою валідною. Немає телепорту
до горизонту. Фрейм має залишатися в межах контактної поверхні (§7);
на краю показується маркер недоступної цілі.

Рух pose згладжується за часом з сталою 40–60 мс; максимальна швидкість
задається в метрах/с і не залежить від fps. Останній валідний target на up
досягається коротким доведенням ≤150 мс. Немає інерційного кидка після up.

## 5. Стан фрейму та захоплення в drift

На фрейм зберігаються pivot у source/rest XZ, world pose `(x,z)`, стан
взаємодії і режим руху `inherited | placed`. Yaw фрейму у v0.2 немає.
`inherited` підкоряється загальному anchored/drift.
`placed` — локально anchored біля нової pose, незалежно від глобального drift.
GUI показує це явно для вибраного фрейму, без прихованого скидання загального mode.
Дія «Відпустити у дрейф» переводить вибраний фрейм у inherited; це окрема дія.

Режим drift стає per-frame: замість однієї uniform `uDrift` симуляція бере
режим фрейму тайла. Перехід `placed↔inherited` іде тим самим механізмом, що й
наявне перемикання anchored/drift (конвенція швидкості в `state3.z`), тому
без стрибка.

Стани жесту: `idle → picking → selected/dragging → settling → idle`.
Стан опори `wet/contact/dry` живе на тайлі, а не на всьому фреймі, і щокроку
виводиться з геометрії (вода, земля, низ тайла), а не накопичується.

На початку drag:

1. Зберегти на CPU початкову pose і режим фрейму для системного скасування.
2. Зафіксувати його поточне взаємне XZ-розташування, навіть якщо drift уже
   розніс деталі. **Не збирати малюнок миттєво в source-контур.**
3. Заморозити горизонтальний стан тайлів і run-ів цього фрейму (drift/anchor
   displacement, швидкість). Перенос додавати спільною pose; хвильова
   вертикаль/нахил лишаються активними.
4. Орбітальний XZ-рух захопленого фрейму пригасити за 100–150 мс і компенсувати
   поточний внесок у capture offset, щоб не було стрибка при захваті.

GPU snapshot не потрібен: горизонтальний стан заморожений, вертикальний
сам повертається до води/опори, стан контакту виводиться з геометрії.
На up нова pose фіксується, фрейм стає placed, локальні anchor-и
переозначаються до захопленої конфігурації. Отже, після переносу рознесений
фрейм не збирається сам; «зібрати оригінальний малюнок» — окрема майбутня
функція, не побічний ефект drag.

При системному скасуванні відновлюється початкова pose і режим; горизонтальний стан
розморожується без змін; висота повторно узгоджується з поточними хвилями за
короткий перехід. Час води не відкручується. Під час settling новий захват
дозволений з фактичної pose. Зміна frame filter не знищує pose прихованих
фреймів; зміна source знищує їх.

Наявний `Tiles → reset` стає повним reset: початкова розкладка, inherited,
нуль локальних станів. Скидання лише вибраного фрейму — окрема явно названа дія.

## 6. Перетворення координат

Поточний `group.matrixWorld` спільний для всього поля, тому рухати ним один
фрейм не можна. Додається pose на фрейм — лише трансляція `(x,z)`;
фрейми не дублюють симуляцію.

Порядок: source/rest → локальне поточне зміщення тайла/run → трансляція
frame pose → field yaw/translation → опора у world XZ → фінальна висота.
Оскільки frame pose не має повороту, зворотне перетворення водних швидкостей
враховує лише field yaw, як зараз.

**Джерело істини — world XZ.** Pose placed-фрейму зберігається у світових
координатах (§5). Трансляція в осях поля, яку бачать рендер і симуляція,
**похідна**: `R(−fieldYaw) · (poseWorld − fieldCenter) − pivot`. Її
перераховують при кожній зміні pose, `fieldYaw` або розміщення поля
(`placeTiles`). Тому при повороті чи переміщенні поля placed-фрейм лишається
на своєму місці у світі, а inherited рухається разом із полем. Без yaw фрейму
(§5) орієнтація малюнка placed-фрейму все одно повертається з `fieldYaw`
навколо його pivot; збереження орієнтації у світі потребує yaw фрейму і
поза обсягом.

**Рендер.** Pose фрейму — матриця об’єкта його мешів: `group → mesh`, де
`mesh.position` = похідна трансляція фрейму в осях поля. Render, depth, reflection,
тіні, підсвічування й ID pass отримують pose штатно через `modelMatrix`;
`instanceMatrix` і CPU-вершини не переписуються.

**Симуляція.** frameIndex тайла пакується у вільні біти `rest1.w` (зараз там
лише bit 0 — polyline); pose і режим фреймів — `uniform vec4 uFramePose[N]`
(xz трансляція, режим). N обмежене бюджетом uniform-векторів; якщо модель має
більше фреймів, ніж влазить, — fallback на маленьку текстуру фреймів (+1
sampler, §9). Polygon і run одного фрейму беруть ту саму pose.
Frame pose застосовується один раз у simulation queries (`waterAt`, контакт)
і один раз у render через matrixWorld; не запікати її у state displacement.

М’яка driftRadius-стінка для вільного фрейму рахується від його поточного
frame anchor, а не старого центра всього поля. Під час drag ця стінка не
бореться з жестом. Початковий layout і повний reset відтворюють старі позиції.

## 7. Контактна поверхня острова

Видимий острів — `PlaneGeometry(ISLAND_SIZE=2400, 384×384)`
([terrainGeometry.js](src/scene/terrainGeometry.js)): регулярна сітка з кроком
6.25 м з пласких трикутників, висоти вершин = `islandHeight` у вузлах.
Тобто видима поверхня **точно** задається 385² висотами вершин.

`islandHeight(x,z)` між вузлами не збігається з мешем, а shore map 512² на
1800 м (крок ≈3.52 м) його лише наближає — жодна з них не є контактною поверхнею.

Запровадити `TerrainContact`:

- Дані: висоти 385² вершин — Float32Array на CPU (≈0.6 МБ) і та сама R32F
  текстура на GPU з `NearestFilter`. Будуються один раз з тих самих вузлів,
  що й меш.
- Висота: `texelFetch` чотирьох вершин комірки, вибір трикутника за
  діагоналлю `PlaneGeometry`, барицентрична інтерполяція. Апаратний bilinear
  (`LinearFilter`) заборонений: він не збігається з трикутниками. CPU і GPU
  виконують ту саму формулу.
- Нормаль: нормаль площини трикутника (кусково-стала).
- Максимум під footprint: на кусково-плаский поверхні він лежить у кутах
  footprint або у вершинах/перетинах ребер сітки всередині нього. Окремої
  max-ієрархії не потрібно.
- Похибка відносно видимого меша — лише float-округлення (≪1 мм).
- Трикутники нижче −34 м викинуті з рендеру, але контактна поверхня там
  лишається визначеною висотами вершин: тайл, що тоне, зупиняється на
  невидимому глибокому дні, а не провалюється.
- За межами `ISLAND_SIZE` контактної поверхні немає: XZ-ціль drag обмежується
  краєм (§4), а вільний тайл там не має опори й поводиться як зараз.

Якщо меш острова колись змінить сітку або отримає vertex displacement у
шейдері, `TerrainContact` має бути перебудований з того самого джерела.

## 8. Перехід вода → берег → суша

Для кожного тайла визначити рівень води `eta`, висоту землі `h`, товщину `t`
і clearance `c` (типово 5 мм).

Плаваючий центр `yWet = eta + t*(0.5-density/(1025*buoyancy))` для достатньої
плавучості. При її нестачі лишається занурення, **але земля зупиняє падіння**.
Ціль опори `yGround` визначається по footprint, не лише по центру.
В обох випадках фінальний низ не проходить крізь землю.

Контакт входить, коли відстань низу до опори ≤2 см, виходить при зазорі
≥5 см. Blend опори змінюється за 150–250 мс. При цьому непроникнення — жорстке
обмеження після blend: згладжування не дозволяє об’єкту провалитися в землю.
Суша не визначається знаком h відносно середнього y=0: у прибої порівнюються
земля, поточна вода й фактичне положення низу. Мокрий тайл може стояти на дні.
`waterAt` над сухою землею не вважається водою: `eta` діє лише там, де
`eta > h`.

Контакт приглушує орбіту, горизонтальний drift і вертикальну швидкість
відносно опори. Після виходу з води вони не лишають прихованої накопиченої
енергії. На суші немає руху від FFT або windage; відрив хвилею дозволений лише
коли підтримка води реально підняла низ над землею більше порога виходу.
Вільний мокрий тайл може знову плисти; placed зберігає frame anchor.

### Нахил тайла

Поточна модель нахилу розрахована на воду й на сушу не переноситься:

- нахил обмежено 20° у двох місцях `TileSim`;
- `surfaceTilt` — малокутове наближення з різниці висот;
- `tileTilt` будує поворот із двох кутів Ейлера.

Для контакту нахил рахується від нормалі опори до повороту (кут між `up` і
нормаллю, без малокутового наближення); межа 20° лишається для води,
на суші робоча межа 55°. Переробка — частина кроку 3 §12.

### Polygon

Плитка лишається твердою. Орієнтація плавно прямує до нормалі опори.
Опорна висота — максимум вимог від усіх нижніх кутів footprint і вершин сітки
всередині нього (§7). Це запобігає врізанню великої плитки в горб,
який не потрапив у чотири попередні точки водної вибірки.
На ввігнутому рельєфі під жорсткою плиткою допустимий проміжок.

На схилі понад 55° XZ-ціль обмежується останнім допустимим положенням фрейму,
а біля pointer показується заборона; без стрибка/перевороту на вертикальну стіну.
Критерій допустимості перевіряє **всю зайняту область контакту**, не тільки pivot.
Порожні місця прямокутника фрейму та глибоке дно під плаваючою частиною
не блокують перенесення через крутий схил, якого малюнок не торкається.
Скелі й обриви з кількома висотами на один XZ — поза моделлю heightfield.

### Polyline

Спільна горизонтальна pose run зберігається, вертикаль повторює рельєф.
Polyline-тайли короткі (у hybrid максимум 0.332 м) проти трикутників рельєфу
(6.25 м), тому укладання **по тайлах у симуляції** достатньо: кожен тайл —
жорсткий сегмент з опорою по своєму footprint і нахилом до нормалі, як polygon.
Профіль рельєфу повторює ланцюжок тайлів. Render-шейдери землю не читають.

На зламі між трикутниками рельєфу сусідні тайли можуть розійтися на
міліметри — це допустимо; на плоскому піску стики збігаються (§11).
Нормалі беруться з повороту тайла, не залишаються водними.

Subdivision ребер у v0.2 немає. Під час load перевіряється максимальна
довжина polyline-тайла; якщо вона перевищує 1 м, статус показує
попередження, а точність контакту для такої моделі не гарантується.

### Порядок перекриття

`aSurfaceOffset` не додається вдруге поверх контактної поправки. Для суші
зберігається малий сталий порядок шарів/груп та внутрішній порядок тайлів,
але він **не відсуває нижню поверхню всього фрейму на метри від рельєфу**.
Clearance, фізична товщина й декоративний bias — окремі величини.
При waveScale=0 та на плоскому піску не має бути z-fighting.

Фрейми можуть перекриватися: фізично один на інший не лягає, обидва стоять
на воді/землі. Видимість перекриття: останній покладений фрейм зверху, без зсуву геометрії.
Для непрозорих матеріалів — `polygonOffset` за рангом розміщення. Прозорі
матеріали мають `depthWrite: false`, тож `polygonOffset` для них не визначає
порядок: їх порядок задає `renderOrder` мешів за тим самим рангом.
Ранг оновлюється на up.

## 9. Рендеринг і ресурси

Pose фрейму в рендері — матриця об’єкта (§6); CPU оновлює лише `position`
мешів одного фрейму. Не переписувати instanceMatrix або CPU-вершини на
pointermove. Розбиття на окремі WebGLRenderer/TileSim для кожного фрейму не
допускається.

Sampler-и TileSim: WebGL2 гарантує 16 fragment samplers, зараз використано 12.
Додається лише висота вершин острова (+1 = 13); frameIndex — у `rest1.w`,
pose — uniform-масив. Fallback-текстура фреймів (§6) дає 14. Фактичні linked
sampler counts перевірити на реалізації, не покладатися на оцінку.
Render-матеріали тайлів (основний, depth, ID, shadow) нових sampler-ів не
отримують: контакт рахується в симуляції.

Bounds: frustum culling мешів іде через `matrixWorld` і тому враховує pose.
Bounding sphere розширюється на drift-зміщення та висоту опори (до вершини
острова) або для мешів тайлів вимикається `frustumCulled`; вибір фіксується
у звіті. Відбиття, depth, підсвічування й тіні використовують спільний чанк
деформації. Якщо тіні поля ще не реалізовані в T4, цю залежність явно
позначити; це не привід здавати неправильні depth або reflection після переносу.

На source=none немає picking pass, контактних ресурсів або слухачів переносу.
Текстура висот острова може бути спільною з іншими підсистемами з явним
володінням. На unload/context lost знімаються pointer capture і listeners,
скасовуються pending reads, видаляються targets/textures/materials.

## 10. Збереження

URL v0.2 зберігає поточні tiles* параметри, але не JSON усіх pose.
Позиції після переносу живуть у сесії; повне перезавантаження відновлює
початкову розкладку. Це має бути очевидно з опису reset/збереження.
Експорт розміщення та відновлення між reload — наступна функція.
Перебудова через frame filter зберігає pose за frameId; зміна масштабу
скасовує активний жест, зберігає world pivot фрейму й перебудовує його footprint.
Зміна `fieldYaw` або повторне розміщення поля скасовує активний жест;
placed-фрейми лишаються на своїх місцях у світі (§6).
Зміна source починає новий layout і не успадковує pose іншої моделі.

## 11. Критерії приймання

| Перевірка | Очікування |
|---|---|
| Hybrid, будь-який з 8 фреймів | Переносяться всі його шари обох конвеєрів; інші фрейми не зсуваються |
| Захват після тривалого drift | Hit по видимій деталі, без повернення до source та без XZ-стрибка >2 см від самого захвату |
| Палець на малюнку / на порожньому місці | Відповідно перенос / камера; камера не смикається перед drag і стартує без затримки |
| Права кнопка над фреймом | Pan камери; фрейм не рухається |
| Берег навскіс через фрейм | Одна частина плаває, інша стоїть на землі; немає загального перемикання висоти |
| Укладання на пагорб 10–45° | Polygon нахиляються, polyline гнеться; фрейм не лишається горизонтальною дошкою |
| Геометрія контакту | Низ не нижче видимого terrain більш ніж на 1 мм; верх/низ не міняються місцями |
| waveScale=0, плоский пісок | Немає мерехтіння перекритих верхніх граней, стики polyline збігаються ≤0.1 мм |
| Два фрейми внахлест | Зверху останній покладений, без z-fighting між фреймами |
| Повернути з суші у воду | Плавний перехід без стрибка >2 см через зміну стану контакту; хвилі відновлюються |
| Недостатня buoyancy | Тайл тоне до дна й зупиняється, не проходить крізь острів, зокрема нижче −34 м |
| Drift до берега без переносу | Inherited-тайли зупиняються на мілині/березі, не проходять крізь острів |
| Відпускання | Нова pose збережена, placed не тягне фрейм до початкового поля |
| placed ↔ inherited | Перемикання без стрибка |
| Blur / pointercancel / втрата capture | Початкове розміщення відновлене, камера доступна, pending hover не починає drag |
| Зміна fieldYaw / повторне розміщення поля | Placed-фрейми лишаються на своїх місцях у світі; inherited рухаються з полем |
| Другий палець | Перенос фіксується, камера отримує нову базу без ривка |
| Горизонт, край острова, крутий схил | Остання валідна ціль і зрозумілий маркер обмеження; жодних NaN/телепортів |
| Mouse й touch на різних DPR | Усталена похибка grab-point ≤5 CSS px; не вимірювати її під час штучно обмеженої швидкості |
| Picking на down | Синхронна зупинка p95 ≤8 мс desktop, ≤20 мс mobile; hover-запити не накопичуються |
| Перезавантаження/масштаб/frame filter | Семантика §10, без стрибків чужих фреймів і втрачених capture |

Продуктивність вимірюється на реальній hybrid-моделі 46 861 тайл, одним
активним фреймом, за однакових розміру viewport/quality. Попередні цілі:
CPU interaction ≤0.5 мс/кадр, додатковий GPU контакт/pose ≤1 мс на desktop;
звіт p50/p95 і мобільний профіль обов’язкові. Це бюджет для перевірки,
не обіцянка поточної швидкості. Без benchmark-пакетів сотень кадрів і
без синхронного повного GPU readback під час жесту.

## 12. Порядок реалізації

1. Frame registry, pose через матриці мешів і `uFramePose` у симуляції,
   per-frame режим placed/inherited; програмне перенесення окремого фрейму на
   воді, узгодження polygon/run, bounds, reset і frame filter.
2. ID pass зі спільною деформацією, синхронний picking на down і арбітр вводу,
   drag/freeze/системне скасування, SurfaceCursor на воді; миша й touch, явна фіксація після up.
3. TerrainContact по вершинах меша з перевіркою проти видимого island mesh;
   нахил від нормалі опори (переробка `tileTilt`/`surfaceTilt`, межа 55°);
   зупинка занурення на дні, опора polygon, береговий blend, контакт для всіх тайлів.
4. Укладання polyline по тайлах, перевірка довжини тайлів при load,
   декоративний bias, перекриття фреймів, обмеження крутих схилів.
5. Reflection/depth/highlight; доступні тіні, lifecycle й ручні
   сценарії §11 на desktop/touch, виміри без прихованого стрес-бенчмарку.

У коді передбачені модулі `TileFrames`, `TileInteraction`, `TerrainContact`
та спільний GLSL чанк деформації для render-матеріалів (основний, depth, ID,
shadow); опору рахує лише симуляція. Остаточні назви не є контрактом.
Наявний Tilecraft залишається лише джерелом компіляції та геометрії.
