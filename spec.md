# Плавучі тайли Tilecraft в Ultra Water — спека

Статус: чернетка v0.1, 2026-11-02.
Область: `Ultra-Water/` (новий модуль `src/tiles/`) + vite-конфіг для імпорту з `tilecraft`.
Tilecraft **не змінюється**: ми лише читаємо його модулі.

## 1. Мета

Завантажити Tilecraft-модель (JSON) **наживо** в сцену Ultra Water і покласти її тайли
на воду як плавучі об'єкти. Обидва конвеєри Tilecraft мають жити одночасно:

- **polygon** (а також `square`/`circle`): кожен тайл — окрема тверда плитка;
- **polyline (LCR)**: кожна група `g` — суцільна стрічка-призма, яка гнеться по хвилях.

Поведінка перемикається одним switch:

- **anchored** — малюнок лишається читабельним: тайли гойдаються, нахиляються й
  описують орбітальний рух хвилі, але пружина тримає їх біля rest-позиції;
- **drift** — тайли (polygon) і стрічки (polyline) дрейфують як уламки.

Перемикання в обидва боки плавне, без телепорту (§6.4).

### Не входить у цю спеку

- Зіткнення тайл–тайл і тайл–CPU-тіло. Тайли в моделі й так перекриваються.
- Контакт з берегом і дном для тайлів (поле ставиться у відкриту воду, §6.5).
- Редагування моделі, кадрові ефекти Tilecraft (wave, stack, mobius, aura).
- Зворотний вплив тайлів на воду (кола, бризки) — лише для промоції в CPU-тіло, §9.
- Зміни в коді Tilecraft.

## 2. Терміни

| термін | значення |
|---|---|
| source units | координати тайлів у JSON (`tile.x`, `tile.y`, y донизу) |
| `space` | результат `createSpace` з Tilecraft: `origin` + `unit` (метри на source unit) |
| тайл | один елемент `layer.tiles[i]`; у цій спеці — одна **точка вибірки води** |
| tile id | глобальний індекс тайла в полі, 0..N-1; він же індекс текселя стану |
| run | одна група `g` polyline-шару; у моделі група живе рівно в одному кадрі |
| owner | тайл, якому належить вершина LCR (`geometry.userData.sourceOwners`) |
| поле | `TileField` — уся завантажена модель на воді |

## 3. Вхідні дані: живе завантаження

### 3.1 Джерела

URL-параметр `?tiles=<src>` і пункт `tiles` у GUI:

- id фікстур Tilecraft (`story-8-frames-hibrid`, `-polygon`, `-polyline`, `demo`, …)
  через `loadFixture(id)` з `core/model-loader.js`. Модифікатори джерела (hibrid,
  polygon) Tilecraft застосовує сам — ми їх не дублюємо;
- локальний файл через drag & drop або file input → `loadFile(file, text)`;
- `none` — поле вимкнено (типово, щоб бенчмарки сцени не змінились).

Типове джерело при `?tiles` без значення — `story-8-frames-hibrid`, бо в ньому
обидва конвеєри в кожному кадрі.

### 3.2 Імпорт модулів Tilecraft у Vite

Корінь Tilecraft задається змінною середовища `TILECRAFT_ROOT`
(типово `D:/work/js-games/ua-dream/tilecraft`). У `vite.config.js`:

- alias `@tilecraft` → `TILECRAFT_ROOT`;
- `server.fs.allow` містить `TILECRAFT_ROOT`;
- **`resolve.dedupe: ['three']`** — обов'язково, **навіть якщо версії однакові**.
  Bare-імпорт `three` з файлу Tilecraft резолвиться від його власного
  `tilecraft/node_modules/three`; дві папки = два екземпляри модуля незалежно від
  версії. Наслідки: `instanceof` між екземплярами хибний, спільний стан модуля
  (`ColorManagement`, `Object3D.DEFAULT_UP`, `Cache`) роздвоюється, three пише
  попередження про кілька копій. Прапорці `isInstancedMesh`/`isMesh` працюють і так.
  Робота йде на three Ultra Water. Версії зведено (2026-11-02): Tilecraft —
  `0.186.1` у `package.json` і в import map `shell/index.html`; dedupe це не замінює.
- Фікстури Tilecraft ходять відносними `fetch` (`../../../.pw-probe/...` від
  `core/`). Їх треба віддавати тим самим dev-сервером: шлях резолвиться від URL
  модуля, тож `fs.allow` на корінь Tilecraft це покриває. Перевіряється у фазі 0.

Збірка (`vite build`) з полем — не мета v0.1: поле працює в `npm run dev`. Якщо
`TILECRAFT_ROOT` недоступний, пункт `tiles` у GUI неактивний, сцена працює як раніше.

### 3.3 Глобальні скрипти

LCR-білдер — класичні IIFE-скрипти, що пишуть у `globalThis`. Порядок важливий:

```js
import '@tilecraft/lib/thickness-scale.js';          // globalThis.thicknessScale
import '@tilecraft/viewer/engines/pixi/polyline-lcr.js'; // globalThis.TilecraftPolylineLCR
```

Імпорт динамічний (`await import(...)`) і лише коли вибрано джерело, щоб сцена без
тайлів не тягнула Tilecraft.

### 3.4 Ланцюжок компіляції

Повторюємо рівно той ланцюжок, що `shell/viewer-session.js` `compileWorld`, щоб
малюнок збігався з Tilecraft один в один:

```
validateModel(model, diagnostics)
  → resolveWorldConfig(inspected, { unitsPerSourceUnit: U }, diagnostics)
  → computeBounds(model, footprintPoints(worldConfig))
  → createSpace(bounds, worldConfig.unit, worldConfig.origin)
  → compileScene(inspected, worldConfig, space, scope, diagnostics)
```

- `U` — параметр `metersPerSourceUnit`, типово **0.05** (модель 1700×600 → ~85×30 м,
  polyline-тайл ~0.33 м). Масштаб навмисно лягає між каскадами 85 м і 12 м: великі
  хвилі гойдають весь малюнок, дрібні — окремі тайли.
- `scope` — `engine/resource-scope.js` Tilecraft; після збору rest (§4) скомпільовані
  меші Tilecraft звільняються, у сцену йдуть лише наші.
- Помилки з `diagnostics` показуються в GUI-рядку статусу; попередження — у консолі.
  Сцена при помилці лишається живою, поле не створюється.

## 4. Rest-дані (знімаються один раз після компіляції)

З `compiled.records` беремо два види records. Точні поля records фіксуються у
фазі 0 (див. §11, П1–П3); нижче — що саме треба дістати.

### 4.1 Polygon / square / circle (`InstancedMesh`)

Для кожного інстансу:

- rest-матриця з `instanceMatrix` → `x, z` (світ, відносно `space`), `yaw`,
  діаметр `d` (scale.x), товщина `h` (scale.y), `y0` (сходинка глибини групи);
- колір з `instanceColor`;
- `tileIndex`, `layerIndex` з `userData.instanceSources[i]`;
- frame id тайла (`tile.f`) і група `tile.g` — з моделі за `tileIndex`.

Геометрію прототипу (`CylinderGeometry`/`BoxGeometry` одиничного розміру) беремо
ту саму, що збудував Tilecraft, — форма тайла визначається лише нею.

### 4.2 Polyline (LCR `Mesh`)

Беремо скомпільовану prism-geometry (`position`, `color`, `index`) як є, плюс:

- `sourceOwners` (Int32 на кожну сиру LCR-вершину; верхня вершина `i + sourceCount`
  має того самого owner, що `i`);
- `runRanges`/`identifyRuns(...)` → для кожного run: `groupId`, `frameId`,
  `tileIndices`, діапазон індексів.

Owner перекладається в tile id поля. Для кожної вершини зберігається **зміщення від
owner-а** в rest: `offset = restPos(vertex) − restPos(owner)` (x, y, z). У вершинний
буфер додаються атрибути `aTile` (float/uint tile id) і `aOffset` (vec3), а `position`
лишається для bounds.

Для кожного polyline-тайла в rest: `x, z` (з `tile.x/y` через `toWorld`),
діаметр `0.5·s·gridSize·scale·unit` (та сама формула, що `roadWidth`), товщина —
висота призми шару, run id.

### 4.3 Фільтр кадрів

Параметр `frame: all | <id>`. Кадри моделі в source-просторі вже розкладені поруч,
тож `all` дає весь малюнок одним полем. Фільтр застосовується при збиранні rest
(тайли інших кадрів у поле не потрапляють) і змінює N — тобто перебудова поля.

## 5. Архітектура

```
src/tiles/
  tilecraftLoader.js   §3: імпорт, ланцюжок компіляції, діагностика
  tileRest.js          §4: records → rest-масиви (CPU, один раз)
  TileSim.js           §6: GPU-симуляція, ping-pong текстури
  TileMaterial.js      §7: патч матеріалу (state → вершина)
  TileField.js         фасад: load / clear / setMode / update(dt) / params
```

`TileField` — сусід `Floaters`, не його частина. У `main.js` він оновлюється в тому ж
місці циклу, що `floaters.step(dt)`, після оновлення `OceanSim` (FFT-текстури
поточного кадру вже готові).

### 5.1 Текстури

N тайлів → текстури ширини `W = 512`, висоти `ceil(N / W)`; tile id → `(id % W, id / W)`.
Для моделі story (46 861) це 512×92.

| текстура | формат | вміст | оновлення |
|---|---|---|---|
| `uRest0` | RGBA32F | `x, z, yaw, radius` | при load |
| `uRest1` | RGBA32F | `y0, thickness, runId, flags` | при load |
| `uState0` ×2 | RGBA32F | `dy, vy, px, pz` (висота над y0, верт. швидкість, горизонтальний зсув від rest) | щокадру, ping-pong |
| `uState1` ×2 | RGBA32F | `tiltX, tiltZ, wX, wZ` (нахил і кутова швидкість) | щокадру, ping-pong |
| `uState2` ×2 | RGBA32F | `vx, vz, prevDispX, prevDispZ` | щокадру, ping-pong |
| `uState3` ×2 | RGBA32F | `prevH, —, —, —` | щокадру, ping-pong |
| `uRun` ×2 | RGBA32F | для кожного run: `px, pz, vx, vz` | щокадру (drift), ping-pong |

`uState0..3` пишуться одним MRT-проходом (4 attachments — у межах гарантованого
мінімуму WebGL2). `flags`: біт 0 — polyline-тайл (горизонталь бере з `uRun`).

## 6. Симуляція (GPU, один прохід на кадр)

Фрагментний шейдер на тексель = тайл. Підключає `WATER_GLSL` з `OceanSurface.js` і ті
самі uniforms поверхні, що `WaterQuery` (`{...surface.uniforms}`), — отже бачить
рівно ту воду, яку малює меш, включно з береговими хвилями.

### 6.1 Вибірка води

На тайл — **4 точки**: центр і 3 точки на колі `0.7·radius` під кутами `yaw + 0°/120°/240°`
(у поточній горизонтальній позиції тайла). Для кожної — `waterAt(q, vec3(0))`.
Разом 4·N оцінок `waterAt` на кадр (~190k для story).

Швидкість води — лише в центрі: `(disp − prevDisp) / dt` з клампом як у
`floaters.ingest` (±3 м/с горизонтально, ±0.8 м/с вертикально). Попередня
зміщення центру зберігається в `uState2`/`uState3`. Після load і після reset
перша оцінка швидкості — 0.

### 6.2 Вертикаль і нахил (обидва режими)

Модель — та сама, що `Floaters.integrate`, зведена до тайла:

- маса `m = ρ_tile · π r² · h`, `ρ_tile = density` (параметр, типово 500 кг/м³);
- для кожної з 4 точок: занурення `sub = clamp((H_i − y_i)/h + 0.5, 0, 1)`, де `y_i` —
  висота нижньої грані тайла в цій точці з урахуванням нахилу;
- сила `F_i = ρw·g·(V/4)·sub·buoyancy` вгору плюс опір
  `−drag·(m/4)·sub·(v_точки − v_води)` (вертикаль ×1.5, як у floaters);
- момент від трьох ободових точок → `tiltX, tiltZ` (малі кути, інерція диска
  `I = m r²/4`); обертання навколо Y не змінюється — `yaw` з rest;
- інтегратор — напівнеявний Ейлер з підкроками у шейдері:
  `steps = min(8, ceil(dt / (1/240)))`; вода між підкроками не перевибирається;
- клампи: `|tilt| ≤ 60°`, `|vy| ≤ 10 м/с`; NaN → тайл повертається в rest
  (захист від зіпсованої текстури).

Очікувана рівновага: тайл сидить з осадкою `h·ρ/ρw` і гойдається з хвилею з
запізненням, а не прилипає до неї.

### 6.3 Горизонталь

**anchored:** `p = orbital + spring`, де

- орбітальна складова — горизонтальне зміщення води в центрі `disp.xz` (з
  `waterAt`), домножене на `orbit` (0..1, типово 1);
- пружина до rest: `a = −k·p − c·v`, критичне демпфування,
  `k = (2π / anchorPeriod)²`, `anchorPeriod` типово 4 с.

**drift:** `a = drag_h·(v_води + wind_drift − v)`, пружини немає.
`wind_drift` — вектор вздовж вітру `OceanSim`, `windage` (типово 0.02) × швидкість
вітру. Обмеження поля: м'яка стінка на відстані `driftRadius` (типово 400 м) від центру
поля, щоб поле не виїхало на острів і за межі видимого.

**Polygon-тайли** рахують горизонталь самі.
**Polyline-тайли** беруть горизонтальний зсув свого run з `uRun`: окремий маленький
прохід на run рахує ту саму формулу по воді в центроїді run. Інакше стрічка
розірветься. Орбітальна складова для polyline-тайлів — власна (щоб стрічка
гнулась), дрейф і якір — спільні для run.

### 6.4 Перемикання режимів

- `drift → anchored`: пружина вмикається з поточного стану; тайли пливуть назад за
  ~`anchorPeriod`, без стрибка.
- `anchored → drift`: пружина вимикається, швидкості зберігаються.
- `reset`: телепорт у rest, обнулення швидкостей і `prev*`.
- Зміна `metersPerSourceUnit` або `frame` — перебудова поля (load заново), не reset.

### 6.5 Розміщення

Центр поля — точка у відкритій воді (типово перед камерою шоту `Flotsam`) плюс
параметр `fieldYaw`. Новий шот камери `Tiles` дивиться на поле згори під кутом ~35°.
Під полем глибина має бути > 5 м — перевіряється через `islandHeight` при
встановленні центру; інакше центр зсувається від острова. Контакт з дном для тайлів
не моделюється (не-мета).

## 7. Рендер

### 7.1 Матеріал

Той самий шлях, що в пропів: `MeshStandardMaterial({ vertexColors })` +
`terrain.patchProp(material)` — тоді тайли отримують атмосферу, підводний туман і
тінь `floatShadow` так само, як ящики й бочки. Поверх цього `TileMaterial` додає
`onBeforeCompile`-чанк, що читає стан:

- **polygon:** `id = gl_InstanceID`; `instanceMatrix` замінюється на
  `T(rest.xz + p, y0 + dy) · R(tiltX, tiltZ) · R_y(yaw) · S(d, h, d)`;
- **polyline:** `id = aTile`; позиція =
  `T(rest(owner).xz + p, y0 + dy) · R(tiltX, tiltZ) · aOffset`.

Нормалі повертаються тим самим `R(tilt)·R_y`. `computeVertexNormals` на CPU
щокадру не викликається ніколи.

Кольори: `instanceColor` і `color` з Tilecraft уже лінійні (`SRGBColorSpace` → linear
у `toRoadPrismBuffers`) — повторно не конвертуються. Прозорі шари (`opacity < 255`)
рендеряться прозорими, як у Tilecraft.

### 7.2 Проходи

| прохід | тайли | як |
|---|---|---|
| основний (opaque) | так | матеріал §7.1 |
| planar reflection | так | `layers.enable(1)`, як пропи |
| floater shadow | так | меші поля в `floaters.scene`-сусідній сцені; depth-only матеріал **теж** з чанком стану (інакше `overrideMaterial` малює rest) |
| refraction / caustics | автоматично | глибина з opaque |

`FloaterShadow.update` вписує камеру по `bodies[{pos, radius}]`. Поле передає туди
одне «тіло»-обгортку: центр поля + радіус bounding-кола поточних позицій (оцінка з
rest + `driftRadius` у drift). Дрібні тайли при тіньовій карті 1024 на полі 85 м
дають ~8 см/тексель — прийнятно; якщо ні — фаза 3 вирішує (окрема карта).

### 7.3 Bounds і culling

Bounding sphere мешів поля задається вручну (rest-bounds + максимальна амплітуда +
`driftRadius` у drift), бо геометрія на CPU не рухається. `frustumCulled` лишається
увімкненим.

## 9. Промоція групи в CPU-тіло (фаза 4)

Клік по тайлу → його група (polygon: усі тайли з тим самим `g`; polyline: run)
перетворюється на справжнє `Body` з `floaters.js`:

- семпли — до 8 точок з `linePoints`/позицій тайлів групи, рівномірно по довжині;
- `volume = Σ π r² h` тайлів групи, `size` — bounding box групи;
- група ховається з поля (flag у `uRest1`), її геометрія копіюється в окремий `Mesh`;
- дає `impacts` (кола й бризки) як інші пропи;
- ліміти `MAX_BODIES = 28` і 512 точок WaterQuery не змінюються; найстаріша
  промоція повертається в поле при переповненні.

## 10. Продуктивність

Бюджет вимірюється вбудованим бенчмарком на шоті `Tiles` (RTX 3060, як у README):

| що | бюджет |
|---|---|
| прохід симуляції (46 861 тайл, 4 вибірки) | ≤ 0.4 мс GPU |
| прохід run-ів | ≤ 0.05 мс |
| opaque з полем, приріст | ≤ 1.0 мс |
| floater shadow, приріст | ≤ 0.3 мс |
| усього кадр шоту `Tiles` | ≤ 6.0 мс (проти 4.6 у Flotsam) |
| компіляція моделі (CPU, при load) | без бюджету кадру; показується в статусі |
| сцена з `tiles=none` | ±0.05 мс від поточних цифр README |

Телефонний профіль: `steps ≤ 2`, 2 вибірки на тайл (центр + 1 обід → нахил лише по
одній осі), без тіні поля. Перевіряється на тому ж OnePlus Nord 4 — ціль 60 fps на
`story-8-frames-polygon`.

## 11. Перевірки фази 0 (до коду симуляції)

Припущення спеки, які треба підтвердити на живому Tilecraft, перш ніж будувати §6:

- **П1.** Поля records `compileScene`: як відрізнити instances-record від road-record,
  де `mesh`, `runRanges`, `layerIndex`.
- **П2.** Семантика `sourceOwners`: це індекс тайла в шарі чи індекс sample-точки
  в `run.points`? Якщо друге — мапа sample → `tileIndex` через `identifyRuns(...).sourceRef.tileIndices`.
  Вершини з owner `−1` (якщо є) — прив'язати до найближчого тайла свого run.
- **П3.** Перевірити, що `loadFixture` через Vite знаходить `.pw-probe/story-rombs-gd.json`.
- **П4.** Один екземпляр three: `THREE.REVISION` у модулі Tilecraft і в Ultra Water однакова.
- **П5.** Кадр Tilecraft і поле в Ultra Water без симуляції (усі `dy = p = tilt = 0`)
  дають той самий малюнок згори — скриншот обох поруч.

Якщо П2 не вдається розв'язати, fallback: owner кожної вершини — найближчий тайл
свого run за rest-xz (рахується один раз при load).

## 12. Критерії приймання

1. `?tiles=story-8-frames-hibrid` завантажує модель; у статусі 46 861 тайл, 2 213 груп,
   обидва конвеєри; консоль без помилок.
2. Згори в спокійній воді (вітер мінімальний) малюнок збігається зі скриншотом Tilecraft
   (П5) — форма, кольори, порядок шарів.
3. **anchored:** через 5 хв симуляції жоден тайл не відійшов від rest далі ніж на
   `2 × амплітуда орбіти` найбільшого каскаду; малюнок читається.
4. **drift:** через 2 хв polygon-тайли розійшлись, polyline-стрічки рухаються
   цілими (жодного розриву стрічки між сусідніми тайлами run більше 1 діаметра).
5. Перемикання `drift → anchored` повертає малюнок за ≤ 3·`anchorPeriod` без стрибків.
6. Тайл з `density = 900` сидить помітно глибше, ніж з `density = 200`; під водою видно
   занурену частину через заломлення.
7. Тайли відкидають тінь на воду й на сусідів; відбиваються в planar reflection.
8. Бюджети §10 виконані; `tiles=none` не змінює цифр README.
9. Помилка у JSON (або недоступний `TILECRAFT_ROOT`) — повідомлення в статусі, сцена жива.

## 14. Ризики

- **Два three.** Без `dedupe` усе завантажиться, але `instanceof` мовчки не спрацює.
  Тому П4 стоїть першою.
- **Розбіжність версій three.** Зараз обидва проєкти на `0.186.1` (Tilecraft —
  точна версія, Ultra Water — `^0.186.1`). Діапазон `^` дозволить Ultra Water
  піти на `0.187+` при `npm install`, і Tilecraft знову виконуватиметься на
  неперевіреній версії. Тому в Ultra Water фіксується точна `0.186.1`, а
  оновлення three робиться в обох проєктах разом.
- **Ціна `waterAt`.** 5× `waterDisplacement` з береговою частиною. Якщо прохід виходить
  за бюджет — варіант без інверсії choppy для ободових точок (лише центр інвертується).
- **Стабільність.** Тонкі тайли (h ~ 8 см) мають власну частоту ~15 рад/с; без
  підкроків явна схема розходиться. Підкроки §6.2 обов'язкові, не оптимізація.
- **Дрейф Tilecraft.** Сигнатури `compileScene`/`resolveWorldConfig` можуть змінитись.
  Усі виклики Tilecraft тримаються лише в `tilecraftLoader.js` і `tileRest.js`.
- **Прозорі шари.** Сортування прозорих інстансів не робиться (як і в Tilecraft);
  можливі артефакти при сильному нахилі.
